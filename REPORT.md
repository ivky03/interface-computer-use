# 1. Architecture

The system is deliberately a small vertical slice with six boundaries: **planner**, **surface adapter**, **artifact recorder**, **policy engine**, **deterministic replay engine**, and **human handoff manager**. Discovery accepts a goal, target, and invocation inputs. `GeminiPlanner` sees a compact observation of the live UI and chooses one typed action at a time. The policy engine validates that action before Playwright performs it. After each successful discovery action, the recorder converts the ephemeral UI reference into a durable locator bundle and parameterizes invocation values. The raw LLM conversation is therefore evidence, not the production capability.

Replay takes only a saved artifact plus typed inputs. It does not call the planner. Each step is policy-checked, located, executed, retried only within its declared bound, inspected for known runtime states, and optionally checkpointed. A final checkpoint is mandatory. Evidence logging and redaction sit alongside both paths. `HumanHandoffManager` owns a session-scoped control lease and can synchronously transfer the same browser page from automation to a human and back.

I chose a local synthetic legacy-bank UI instead of a public commerce site. It gives repeatable member lookup, sub-account preparation, not-found, session-expired, permission-denied, and irreversible-confirmation states without real credentials, PII, terms-of-service risk, or external flakiness. Playwright is the concrete web adapter because it provides both semantic locators and browser-level interaction. I intentionally did not introduce queues, databases, workers, or a service mesh: the assignment's load-bearing question is whether the capability contract and execution semantics are correct, not whether scaffolding can be scaled prematurely.

# 2. Artifact schema

`CapabilityArtifact` is a versioned, human-reviewable contract. It contains capability identity/version, logical application and vendor identity, portable entrypoint, allowed origins, typed parameters, typed outputs, ordered typed steps, and a required success checkpoint. Each step carries an action, target, optional parameterized value/output binding, risk class, timeout/retry bound, and optional step checkpoint.

Targets use an **ordered locator bundle**, not one selector. The web recorder prefers accessible labels/roles and stable control names, then falls back to a structural CSS selector. The ephemeral `data-cua-eid` used to let the LLM point at the current observation is never serialized. The locator vocabulary also reserves surface-neutral strategies (`accessibility`, `visual_text`, `coordinate`) so the artifact does not require every future surface to have a DOM. A concrete input such as a member number is stored as `{{member_id}}`, and the goal description is parameterized too; invocation values are not baked into the capability.

The artifact is intentionally more than a macro. Inputs tell a calling agent what it must supply; outputs define what it gets back; the success checkpoint says what “done” means; risk says whether automation may perform a step unattended. This makes the artifact a plausible agent-invocable capability rather than a transcript replay.

# 3. Determinism & error handling

Replay contains no LLM decision call. Determinism comes from the fixed step order, strict typed input validation, parameter substitution, ordered stable locators, bounded waits/retries, explicit runtime-state detection, mandatory output-contract validation, and a mandatory final checkpoint. Discovery can be stochastic; once accepted, the artifact is not.

Errors are classified by meaning rather than by exception type. `MEMBER_NOT_FOUND` is a **business outcome**: the caller receives a valid result saying there is no record. `SESSION_EXPIRED` is **recoverable**: the executor recognizes the known interstitial, performs a separately bounded recovery (`Continue session`), and then executes the original step; recovery does not silently consume an action retry. `PERMISSION_DENIED`, unknown locator/checkpoint failures, output-contract violations, and application errors are **hard failures** and stop with step/checkpoint context, expected state, observed state, and a screenshot. Policy violations are a separate failure class. This separation prevents two dangerous production behaviors: retrying legitimate business outcomes forever, and silently continuing after a state that invalidates subsequent steps.

Locator drift is secondary in the stated environment but still handled deliberately. Each target has multiple strategies and each must resolve uniquely; ambiguous matches are rejected instead of guessed. If all strategies fail, replay stops with evidence. With more time I would add offline locator-health scoring and controlled tenant overlays rather than an open-ended LLM recovery loop.

# 4. Heterogeneity & multi-tenant

The intended seam is **artifact semantics vs. surface mechanics**. The artifact says “click this target,” “read this output,” and “verify this checkpoint”; the adapter decides how those concepts map to the current surface. The concrete `PlaywrightSurface` can use roles, labels, text, names, or CSS. A legacy web adapter could add frame context, accessibility paths, OCR text anchors, and normalized coordinates. A desktop adapter could resolve the same `accessibility` or `visual_text` strategies through UI Automation/AX APIs and execute OS-level click/type actions. The flow, input/output contract, risk classification, and result taxonomy do not need to change.

For multi-tenant reuse, I would key the base capability by **vendor product + capability version**, not tenant. Tenants would reference the base artifact plus a small variant overlay containing only changed entry routes or target strategies. The current schema already carries `vendor_product`, `tenant_variant`, and capability version as the identity seam; I deliberately did not build the registry/overlay store. At onboarding or version change, a canary replay would compare checkpoints and locator resolution. A compatible tenant keeps using the base capability; a known variant receives an override; unresolved drift moves the capability to review instead of silently self-healing. That is safer for regulated workflows than letting every tenant mutate its own learned macro.

# 5. Escalation & handoff

Escalation can be raised because discovery is stuck/maxed out, replay hits an unrecoverable condition, or policy classifies a step as irreversible. The intervention request records capability/goal, step, reason, current session URL, screenshot, and session identity. The handoff manager then transfers an explicit `ControlLease` from `automation` to `human`; the executor checks that it owns the lease before acting.

The minimal operator mechanism is intentionally real rather than a fake “TODO”: in headed mode the exact same Playwright browser/page remains open, automation pauses, and the human operates that window. Browser event capture records the human's clicks/change events (typed values are redacted). After the operator signals completion, ownership transfers back to automation and replay resumes on that exact page/session and verifies the checkpoint. Tests use an operator callback to exercise the identical seam without requiring a person during CI. A production version would replace terminal signaling with an authenticated operator console/CDP or streamed-session control channel, but the ownership and resume semantics would remain the same.

# 6. Safety

Safety is enforced on **both discovery and replay**, not only in the prompt. `policy.json` defines permitted origins, logical routes, path prefixes, and action types; replay also checks that an artifact's entrypoint remains inside that artifact's own declared origin contract. Every step has a risk class. The configured policy requires human control for irreversible actions; a different deployment can fail closed and hard-block them. Targets must resolve uniquely, and final success is asserted against visible state rather than assumed.

Sensitive data is separated from capability data. Invocation values are converted to placeholders before serialization (including numeric/bool values emitted by a planner), and logs use parameter-aware redaction plus patterns for tokens/passwords, SSNs, payment-card-like numbers, email addresses, and monetary values. Model API credentials come only from environment variables, are sent in the Gemini API authentication header rather than the request URL, and are not logged. Failure screenshots remain a residual sensitive-data risk in a real bank environment; production storage therefore needs tenant-scoped encryption, short retention, access controls, and screenshot redaction/DLP before persistence. This project keeps the target entirely synthetic to avoid pretending those controls are already production-grade.

# 7. Cuts

I deliberately did **not** build multi-tenant infrastructure, desktop automation, a remote co-browsing console, a capability database/catalog service, approval workflows, or open-ended LLM self-healing. Those would increase breadth without proving the core execution model. The repository keeps the scripted planner trace explicitly labeled `SCRIPTED-not-live`, while `/evidence/discovery.jsonl` and `/evidence/capability.json` contain a genuine Gemini-driven discovery run. The resulting artifact was then replayed deterministically with a different synthetic member input.

Next, I would add one stretch goal only: **canonicalized tenant overlays with multi-run stability scoring**. I would replay approved capabilities N times across two slight UI variants, record locator/checkpoint success rates, and gate unattended use on an approval state. That directly tests the assignment's real-world concern—safe reuse across institutions running variants of the same vendor product—without obscuring the core with unrelated features.
